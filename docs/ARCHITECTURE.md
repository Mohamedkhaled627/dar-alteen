# معمارية مشروع دار الطين

تحديث: 2026-11-04. الوثيقة دي بتجاوب "ليه اخترنا كده". الشرح التقني للكود نفسه موجود في PROJECT-OVERVIEW.md و AGENTS.md.

# 1. القرارات المعمارية وسببها

static frontend بالكامل (HTML و CSS و Vanilla JS) بلا سيرفر ولا build step:
الموقع كتالوج عرض + طلب واتساب، فمش محتاج backend أصلا. الصيانة صفر تقريبا، وأي تغيير بيتعمل بتعديل الملف مباشرة.

طلب على واتساب مباشر (wa.me برسالة مُجهزة: منتج + كمية + إجمالي):
قناة البيع الحقيقية للتجار الصغير في مصر. مفيش سلة ولا دفع إلكتروني ولا checkout ولا حسابات ولا أي API: الطلب كله بيصير بره الموقع في واتساب البائع. أي ميزة شراء إلكتروني هنا كانت هتزود تطوير ورسوم ومسؤوليات قانونية مش يحتاجها السوق ده.

كتالوج في localStorage على جهاز البائع (والافتراضي في store-data.js):
البائع بيدير منتجاته من جهاز واحد بس (قرار محسوم). ده كفاية لتاجر صغير بكتالوج من 10 لحد 30 منتج تقريبا، ومن غير تكلفة سيرفر ولا تسجيل. أي تعديل ثابت لازم يوصل للزوار بيتعمل في DEFAULT_PRODUCTS في store-data.js وبرفع الملف مع الموقع.

استضافة مجانية على subdomain (GitHub Pages أو Netlify أو ما شابه):
الموقع ملفات ثابتة بتتوزع من CDN، وبيتحمل آلاف الزوار يوميا بدون تكلفة أو صيانة على الإطلاق

# 2. حدود القرارات - بصراحة

الكتالوج مش مُشترك بين الأجهزة:
اللي البائع يسجله في admin بيتحفظ في localStorage على جهازه هو بس. الزائر الجديد على أي جهاز بيأخذ DEFAULT_PRODUCTS المرفوعة مع الموقع. فتحديث الكتالوج للزوار يعني تحديث ملف store-data.js ورفع الموقع تاني. ده مقبول تماما للمرحلة دي (إدارة جهاز واحد).

واتساب بلا تتبع:
مفيش سجل طلبات في الموقع ولا أناليتيكس ولا إحصائيات: الطلبات كلها بتوصل على واتساب البائع مباشرة. لو البائع حاب يعرف الترافيك لاحقا، الأناليتيكس إضافة بسيطة على static (زي GA أو Plausible).

استضافة مجانية subdomain:
بتربط الموقع على subdomain، ولو دومين حقيقي اتربط لاحقا ده تعديل DNS بس - كل المسارات relative فمفيش تعديل في الكود.

# 3. مسار الترقية لو البيزنيس اتوسع

مرحلة 1: كتالوج JSON مُشترك (static). يضاف catalog.json ثابت مرفوع مع الموقع، بيتقرا في store-data.js بfetch قبل الـ localStorage. البائع يعدل من admin زي ما هو، ويصدّر ثم يرفع الملف. حل مشكلة عدم المشاركة من غير سيرفر ولا تكلفة إضافية (همّه: يتعمل زر تصدير JSON في admin).

مرحلة 2: Supabase (لو البائع عايز يعدل من جهاز تاني / موبايل). عوّض loadProducts/saveProducts لطبقة Supabase REST، فالكتالوج يبقى مُشترك عالميا. الرندر والفلترة وواتساب مش هيتأثروا - كله واقف على نفس الfunctions في store-data.js.

الفرق الوحيد بين المرحلتين: مين بيكتب الكتالوج. الـ render والتصفح والواتساب مش هيتغير في الحالتين

# 4. تدفق المستخدم (مفيش auth ولا API)

زائر يفتح الموقع، بيمشي كده:
1. الرئيسية (hero + أقسام + مختارات + خطوات الطلب)
2. المتجر (بحث + ترتيب + فلاتر تصنيفات)
3. تفاصيل منتج (كمية من 1 لـ 10 + الإجمالي)
4. زر واتساب بياخد الرسالة المُجهزة (المنتج + الكمية + السعر) وبيسلّمها خلاص

مسؤولية الموقع تنتهي عند تجهيز الرسالة وفتح واتساب - البيع نفسه بيحصل بره الموقع. كل views موجودة في index.html نفسها وبتتقلب بالhidden (SPA بسيط بلا routing حقيقي)، ومفيش ولا طلب API من أول فتح الصفحة لآخر زر واتساب.

# 5. scale - ليه مفيش سيرفر مش مشكلة

الموقع ثابت: ملفات بتطلع من CDN، فالاستضافة المجانية بتتحمل آلاف الزوار يوميا بدون تكلفة أو عناية. مفيش API ولا قاعدة بيانات يقدروا يعطلوا: حتى لو الترافيك زاد عشر أضعاف، الاستضافة بتتحمل. والطلب بيروح واتساب البائع مباشرة، فمفيش حمل على الموقع في أول مكان.

القيد الحقيقي مش عدد الزوار: هو حجم الكتالوج. الـ localStorage بتاع المتصفح محدود (في حدود 5MB)، ولوحة admin بتضغط الصور (compressImage) عشان توفر مساحة. لو الكتالوج وصل 30 أو 40 منتج بصور حقيقية، هيبدأ يضيق - وساعتها مرحلة 1 (الـ JSON المُشارك) هترفع السقف ده بالكامل.

# 6. حدود الأمان - بصراحة

لو حد من بره فتح admin على جهازه هو: مش هيلاقي حاجة، لأن الـ localStorage بتاعه على جهازه فاضي، فهياخد الـ DEFAULT_PRODUCTS بس. مفيش بيانات عملاء ولا دفع ولا حسابات أصلا، فمفيش حاجة تتسرّب أصلا - الصفحة بالنسبة له فاضية.

لو جهاز البائع نفسه اتخترق: أي حد فتح المتصفح عليه بيشوف الكتالوج واللوحة. ده نفس التهديد لأي ملف على الجهاز - مش مشكلة معمارية للموقع، وتحته حماية الجهاز نفسه (password + تشفير) مش شغل الموقع.

private browsing أو localStorage مقفول: لوحة admin بتظهر تنبيه (storageAvailable) لأن التعديلات مش هتتخزن session-level بس. ده على البائع بس، الزائر ميتأثرش لأنه بياخد defaults ثابتة.

مفيش backup: مفيش نسخة احتياطية من الكتالوج غير على جهاز البائع. لو الجهاز ضاع، آخر نسخة هي الـ defaults المرفوعة مع الموقع. الحل: تصدير الكتالوج كـ JSON كل فترة (زر تصدير JSON في admin هيغطي ده - مرحلة 1).

ميزة إضافية: مفيش سر ولا مفتاح API ولا secret في الموقع أصلان، فنشره مفيش فيه أي خطر تسريب - كل الـ secrets بتاعة التوسع المستقبلي (Supabase) هتكون في مكان واحد بس.

كلمة سر لوحة admin (حماية UX مش سياسة سيرفر):
- أول فتح: البائع بيفترض كلمة سر (6 حروف على الأقل + تأكيد)، وبينتقل **hash SHA-256** بس في localStorage بمفتاح `dar-alteen-admin-pw` - النص الأصلي مش محفوظ في أي مكان.
- كل فتح بعد كده: شاشة دخول، والنجاح بيفتح اللوحة في **sessionStorage** (`dar-alteen-admin-unlocked`) يعني القفل بيتقفل مع قفل التاب. فيه زر "قفل" ولوحة وزر "تغيير كلمة السر" (بيطلب الحالية أول).
- بصراحة: دي حماية UX ضد الفتح العرضي/السريع على جهاز البائع مش حماية سيرفر. أي حد عنده وصول كامل لجهاز البائع يقدر يقفل الكومبيوتر في وضع devtools أو المطور بيتع الغطاء كله - التهديد ده بيتحل بحماية الجهاز نفسه (حساب مستخدم بكلمة مرور)، مش بكود الموقع. ومفيش lockout بعد محاولات فاشلة لأن أي عداد JS يتقدر تجاوزه بنفس السهولة.
- في وضع التصفح الخاص (localStorage مقفول)، كلمة السر نفسها بتتخزن session-only زي الكتالوج.
- crypto.subtle بيتبعت SHA-256 في file:// و https (سياق آمن) - لو مش متاح، الشاشة بتقول للمتصفح يستخدم متصفح حديث.

حصر مصادر صور المنتجات (`StoreData.isSafeImageSrc`):
- الرندر بيقبل بس: `data:image/jpeg|png|webp;base64` أو مسار نسبي محلي (assets/stock/...). أي scheme تاني - http: و javascript: و data:image/svg+xml - مرفوض، والرفض بيجري في `normalizeProduct` نفسها (trust boundary) فأي منتج بصورة مخالفة مش بيدخل الكتالوج أصلا.
- الأثر الوظيفي: حقل "رابط صورة" في admin بقى مايقبلش روابط https خارجية - اختار صورة من الجهاز (بيضغطها لـ data:image/jpeg) أو مسار محلي من المشروع.

XSS escaping مشترك:
- `StoreData.escapeHtml` هي الدالة الوحيدة المسماة للـ escaping، وكل innerHTML في app.js و admin.js propia بيخرج منها: id/name/alt/desc/specs/مصدر الصورة - كلهم escaped قبل ما يتكتبوا.

بيانات العملاء غير موجودة بالهندسة:
- مفيش تسجيل دخول ولا سلة ولا سجل طلبات ولا أناليتيكس في الموقع أصلا. الطلب بييجي رسالة واتساب بره الموقع، فمفيش PII يُخزَّن أو يُتسرّب أصلا - ده أفضل حاجز أمني ممكن: مفيش داتا أصلا.

# 7. مسارات مستقبلية (مش مبنية - مقصود)

- robots.txt: موجود (بيمنع admin.html وبيسمح للباقي) + meta robots `noindex, nofollow` داخل admin.html نفسها (double protection لو robots.txt انضغط)
- sitemap: لما الدومين يتربط وينشر، ملف واحد صغير يتضاف
- Schema.org (LocalBusiness أو Product): يتضاف في index.html لما معلومات التواصل الحقيقية تتثبت
- PWA أو service worker: خارج الـ scope (تخزين offline مش مهم لكتالوج بطلب واتساب)
- أناليتيكس: إضافة بسيطة على static لاحقا لو البائع حاب يعرف ترافيك الموقع
